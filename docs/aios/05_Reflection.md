# 71. ORGANIZATIONAL LEARNING

The repository SHALL accumulate experience.

Every execution session must improve not only
the project,

but also

the way the project is produced.

Learning is a permanent repository asset.

---

# 72. REFLECTION PHASE

Reflection SHALL execute after verification
and before checkpoint generation.

Execution order

Planning

↓

Implementation

↓

Verification

↓

Reflection

↓

Documentation

↓

Checkpoint

Reflection is mandatory.

---

# 73. PURPOSE OF REFLECTION

Reflection exists to answer four questions.

What worked well?

What failed?

Why did it happen?

How can future engineers avoid repeating it?

Reflection SHALL improve future execution.

Not evaluate past execution.

# 75. ANTI_PATTERNS.md

Purpose

Document practices that SHALL NOT be repeated.

Examples

Duplicating canon

Implementing before understanding requirements

Large undocumented commits

Ignoring dependency changes

Modifying Story Bible without Timeline review

Hardcoding narrative values

Every anti-pattern shall explain

Why it occurred

Its consequences

How to detect it

How to avoid it

---

# 76. SUCCESS PATTERNS

Successful execution strategies SHALL also be recorded.

Examples

Incremental scene production

Documentation-first workflow

Repository checkpoint before context exhaustion

Dependency-first implementation

Knowledge-first planning

Good practices deserve documentation.

---

# 77. ROOT CAUSE ANALYSIS

Every significant issue SHALL receive
a root cause analysis.

Symptoms are not causes.

The repository shall distinguish between

Problem

↓

Cause

↓

Underlying Cause

↓

Systemic Cause

Corrective action targets causes.

Not symptoms.

---

# 78. FIVE WHYS

The Five Whys method SHOULD be used
for recurring issues.

Example

Scene inconsistent

↓

Why?

Timeline outdated

↓

Why?

Timeline changed

↓

Why?

Dependency review skipped

↓

Why?

No workflow enforcement

↓

Why?

Repository process incomplete

The solution addresses the process.

Not merely the symptom.

---

# 79. PREVENTIVE ACTIONS

Every resolved issue SHALL produce
at least one preventive action.

Possible actions

New documentation

Workflow improvement

Automation

Validation rule

Checklist

Architecture change

Repository policy

Never resolve an issue
without reducing the chance of recurrence.

---

# 82. ASSUMPTION REGISTER

All assumptions SHALL be documented.

Every assumption contains

Description

Reason

Confidence

Evidence

Validation Status

Expiration Condition

Assumptions are temporary.

Facts are permanent.

The repository shall clearly distinguish between them.

---

# 83. KNOWLEDGE CONFIDENCE

Every important knowledge item SHOULD
include a confidence level.

Confirmed

High Confidence

Medium Confidence

Low Confidence

Unknown

Low-confidence knowledge SHALL NOT
be treated as canon.

---

# 84. KNOWLEDGE PROMOTION

Knowledge progresses through stages.

Idea

↓

Hypothesis

↓

Proposal

↓

Reviewed

↓

Approved

↓

Canon

Only Canon is authoritative.

Earlier stages remain traceable.

---

# 85. EXECUTION FEEDBACK LOOP

At the end of every execution

Evaluate

↓

Reflect

↓

Learn

↓

Improve Process

↓

Continue

This loop never ends.

---

# 86. DEFINITION OF LEARNING

Learning is demonstrated only when

future execution improves.

Recording observations without
changing future behavior
does not constitute learning.

---

# 87. STUDIO MEMORY

The repository SHALL function as
the institutional memory of the studio.

No critical production knowledge
may exist exclusively inside

individual engineers,

chat histories,

or AI context windows.

Knowledge belongs to the project.

Not to the contributor.
